# MAX 26.7.0 graph API → `mo`/`rmo` op inventory

Ground truth from `max.graph` (MAX 26.7.0, `/work/spikes/max/.venv`), recorded 2026-11-11. Each
entry was built in its own tiny graph and printed; nothing here is guessed from docs. Raw IR: `spikes/max/work/inventory/<group>.txt`,
regenerated by the scripts (custom syntax from `print(g)`; generic form of the whole
module, with properties, for representative cases). Scripts: `capi/scripts/inventory/` (run each with `$MAX_VENV/bin/python -I`, after `. ./env.sh`).

## 0. Level, form and conventions (read first)

**Level.** What MAX's Python API emits and what `mnist/src/Graph.elm` emits are the *same level*:
a mix of three op-name families, all in one `mo.graph`. Nothing lowers `rmo` to `mo` on the way
in; MAX's compiler does that itself (the hand-lowered `capi/models/mlp_mo.mlir` fails to verify).
Every entry below is at this level, which is the level an Elm DSL should write.

| Family | What it is | Examples |
|---|---|---|
| `rmo.<op>` | "relaxed" ops with their own definitions: implicit broadcasting, safe dtype promotion, shape inference | `rmo.add`, `rmo.matmul`, `rmo.reshape`, `rmo.concat`, `rmo.slice`, `rmo.select`, `rmo.conv`, `rmo.top_k` |
| `rmo.mo.<op>` | the `rmo` wrapper of a `mo` op | `rmo.mo.relu`, `rmo.mo.reduce.add`, `rmo.mo.transpose`, `rmo.mo.range`, `rmo.mo.gather` |
| `mo.<op>` | plain `mo` ops, emitted directly | `mo.constant`, `mo.cast`, `mo.custom`, `mo.split`, `mo.reduce.layer_norm`, `mo.if`, `mo.while`, `mo.call` |

Graph.elm uses exactly these spellings today (`mo.constant`, `mo.cast`, `rmo.<bin>`, `rmo.matmul`,
`rmo.mo.<unary>`, `rmo.mo.reduce.<x>` with `axis`, `rmo.reshape` with `newShape`, `rmo.mo.transpose`
with a permutation constant, `rmo.mo.range` with three scalar constants), so no translation step
exists or is needed.

**Two print forms.**
- *Custom syntax* (`print(g)`, Graph.elm `print`): attributes in `[...]` after the operands, e.g.
  `rmo.mo.reduce.add(%x) [axis = 1] : (...) -> ...`.
- *Generic form* (Graph.elm `toModule` → MlirBc): MLIR properties `<{...}>`, e.g.
  `"rmo.mo.reduce.add"(%x) <{axis = 1 : index, outputParamDecls = #kgen<param.decls[]>}>`. When
  an LLVM without the `mo` dialect writes the bytecode, these must go in as ordinary attributes
  `{...}` (README; `capi/scripts/props_to_attrs.py`); MAX rebuilds the properties itself.

**Fields Python emits that Graph.elm leaves out, and gets away with** (the MNIST run proves these
are optional): `outputParamDecls = #kgen<param.decls[]>` on almost every `rmo.*` op (needed
non-empty only when the op *introduces* a new symbolic dim, §11), `mo.chain.create()` as `%0` in
every graph (needed only when something consumes a chain: §9, §10, §12), `counter = N : i64` on
`mo.graph`, `_kernel_library_paths = []`, `parameters = #kgen<exprs[]>` on `mo.output`/`mo.yield`,
and the module attribute `mo.device_info_mapping = {cpu = #M.device_info<"cpu", "cpu", "unknown", "cpu">}`.

**Re-parse check.** Every custom-syntax graph printed here (205) was parsed and verified again
by MAX's own MLIR parser (`capi/scripts/inventory/reparse.py`): all pass.

**Types and literals.**
- Tensor: `!mo.tensor<[2, 3], f32>`, scalar `!mo.tensor<[], f32>`. Dtype names: `f32 f64 bf16
  si32 si64 ui8 ui64 bool`. Inside a constant's `tensor<>` type, bool is `i1`.
- Symbolic dims: `!mo.tensor<[batch, 3], f32>`; algebraic: `[mul_no_wrap(n, 3)]`, `[add(a, b)]`,
  `[add(n, -2)]` (§11).
- Constant: `mo.constant <#M.dense_array<v1, v2, ...> : tensor<2x2xf32>> : !mo.tensor<[2, 2], f32>`
  (generic: `"mo.constant"() <{value = #M.dense_array<...> : tensor<2x2xf32>}>`). Row-major flat
  values. Scalar: `tensor<f32>`; bool `#M.dense_array<true, false> : tensor<2xi1>`. Floats print as
  `2.000000e+00`, `9.99999974E-6`, `0.00392156886` (all accepted).
- Shape attributes: `#mosh<ape[2, 3]> : !mosh.ape` (used by `newShape`, `starts/stops/steps`,
  `strides`, `paddings`, `filter_shape`, `shape`, ...).

**Axes: three different encodings.** This is the main irregularity:
1. `index` attribute, non-negative (Python normalises): `rmo.mo.reduce.*`, `rmo.mo.reduce.softmax`
   / `logsoftmax`, `rmo.mo.cumsum`, `rmo.mo.gather`, `rmo.mo.scatter`, `rmo.concat`, `mo.split`.
   Custom syntax prints `[axis = 1]` (reduce/gather/split) or `[axis = 0 : index]` (concat);
   generic always `axis = 1 : index`. Exceptions to "non-negative": `softmax`/`logsoftmax` only
   normalise `-1` (axis `-2` goes through as `axis = -2`), and `concat` passes negatives through
   (`axis = -1 : index`). See the compile probes at the end of this file.
2. `si64` attribute: `rmo.top_k` (`k = 2 : si64, axis = -1 : si64`), `rmo.conv` (`num_groups = 1 : si64`).
3. Operand tensor: permutation of `rmo.mo.transpose` (si64[rank] constant); `rmo.mo.bottom_k`
   (k, axis, sorted as scalar operands); `rmo.mo.linalg.band_part` (num_lower, num_upper, exclude).

**Reductions keep the reduced dim** (size 1). There is no keepdims flag; Python gets "drop the
dim" from a following `rmo.reshape`.

**Broadcasting is implicit.** `rmo` element-wise ops (and `rmo.select`, `rmo.matmul` batch dims)
broadcast numpy-style themselves; the Python API never inserts `broadcast_to` for them.
`rmo.broadcast_to` exists only for an explicit `ops.broadcast_to`. Incompatible shapes fail at
graph-build time: *"Input lhs (shape [2, 3]) dimension at axis 1 (value 3) and input rhs (shape
[4]) dimension at axis 0 (value 4) are neither equivalent nor broadcastable. Insert an explicit
rebind if these dims will be equivalent at runtime."*

**Dtype promotion.** `rmo` binary ops also promote *safe* mixed dtypes in the op itself:
`rmo.add(f32, f64) -> f64`, `rmo.add(si32, si64) -> si64`, `rmo.matmul(f32, f64) -> f64`.
Unsafe mixes fail at build: `f32 + si64` → *"Unsafe cast from si64 to f64. Insert an explicit cast
op"*. Python scalars ("weak" values) become a rank-0 `mo.constant` of the other operand's dtype
(`x + 2.0` → `mo.constant ... tensor<f32>` then `rmo.add(x[2,3], c[])`); a Python float with an int
tensor is refused in Python (*"Can't promote python float to dtype(DType.int64)"*).

**Dtype restrictions seen.** The Python sources check almost nothing; the op verifiers check at
build time only: `rmo.mo.not` (*"operand #0 must be boolean element type"*), `rmo.and/or/xor`
(*"Inputs must be bools"*), gather indices must be integer (Python). Float-only math (`exp`,
`log`, `sqrt`, `sin`, `tanh`, `erf`, `floor`, `sigmoid`, `gelu`, `is_nan`, `acos`, `mean`) all
*build* on si64 input: see the compile probes at the end for what then happens.

## 4. Reductions  (`work/inventory/g4_reduce.txt`)

Common shape: `%r = rmo.mo.reduce.<k>(%x) [axis = 1] : (!mo.tensor<[2, 3, 4], f32>) -> !mo.tensor<[2, 1, 4], f32>`;

## 7. Convolution and pooling  (`work/inventory/g7_conv.txt`, `g13_extra.txt`)

Default layouts: input **NHWC**, filter **RSCF** = `(kh, kw, in_channels/groups, out_channels)`.
The filter layout is carried **in the filter's type**, set by a `rmo.rebind_tensor_shape` the
API inserts before every conv:

```
%f = rmo.rebind_tensor_shape(%w) [message = ""] : (!mo.tensor<[3, 3, 3, 4], f32>) -> !mo.tensor<[3, 3, 3, 4], f32, {layout = #mo.layout<RSCF>}>
%y = rmo.conv(%x, %f) [strides = #mosh<ape[1, 1]> : !mosh.ape, dilations = #mosh<ape[1, 1]> : !mosh.ape, paddings = #mosh<ape[0, 0, 0, 0]> : !mosh.ape, num_groups = 1] : (!mo.tensor<[1, 8, 8, 3], f32>, !mo.tensor<[3, 3, 3, 4], f32, {layout = #mo.layout<RSCF>}>) -> !mo.tensor<[1, 6, 6, 4], f32>
```
generic: `"rmo.conv"(%x, %f) <{dilations = #mosh<ape[1, 1]> : !mosh.ape, input_layout = "NHWC", num_groups = 1 : si64, paddings = #mosh<ape[0, 0, 0, 0]> : !mosh.ape, strides = #mosh<ape[1, 1]> : !mosh.ape}>`.
`input_layout = "NHWC"` is a string property, hidden in custom syntax when it is the default.

| Python | IR | notes |
|---|---|---|
| `conv2d(x, w, stride, dilation, padding, groups, bias)` | rebind + `rmo.conv` as above | `strides`/`dilations` `#mosh.ape[h, w]`; `paddings` `#mosh.ape[4]` in the order given (Python docs: top, bottom, left, right); `stride (1,2), dilation (2,1), padding (0,1,2,3)` → `[1,5,6,4]`. `groups=3` → `num_groups = 3` with filter `[3,3,1,6]`. `bias` → a separate `rmo.add(%y, %b)` (implicit broadcast over last dim) |
| `filter_layout=FCRS` | same, with `{layout = #mo.layout<FCRS>}` on the rebind's result type | filter `[F, C, R, S]` |
| `input_layout=NCHW` | adds `input_layout = "NCHW"` to the custom-syntax attribute list | builds with x `[1,3,8,8]`; it inferred output `[1,6,6,4]` (NHWC-shaped); not compiled |
| `conv2d_transpose(x, w, stride, dilation, padding, output_paddings, bias)` | rebind (RSCF; filter is `(kh, kw, out, in)`) + `rmo.conv_transpose(%x, %f) [strides = ..., dilations = ..., paddings = #mosh<ape[0, 0, 0, 0]>, output_paddings = #mosh<ape[0, 0]>]` | `[1,8,8,3]`, stride 2 → `[1,17,17,4]`; padding 1 + output_padding 1 → `[1,16,16,4]`. Python requires output_padding < stride |
| `conv2d_transpose(..., bias=b)` | **fails at build in MAX 26.7** for NHWC: the bias path does `permute [0,2,3,1]`, `add`, `permute [0,3,1,2]` (it assumes NCHW output), giving `[1,16,4,16] + [4]` → broadcast error. Add the bias yourself with `rmo.add` |
| `avg_pool2d(x, kernel, stride, dilation, padding, ceil_mode, count_boundary)` | `rmo.avg_pool(%x) [filter_shape = #mosh<ape[2, 2]> : !mosh.ape, strides = ..., dilations = ..., paddings = #mosh<ape[0, 0, 0, 0]> : !mosh.ape, ceil_mode = false, count_boundary = true]` | NHWC; Python widens `padding=(ph, pw)` to `[ph, ph, pw, pw]`; generic sorts the properties alphabetically |
| `max_pool2d(...)` | `rmo.max_pool(%x) [filter_shape, strides, dilations, paddings, ceil_mode = false]` | no count_boundary |

## 8. Random  (`work/inventory/g8_random.txt`)

The seed is an **operand**: a `!mo.tensor<[1], ui64>`. There is no attribute, global state or chain
in the IR. Python keeps a per-graph seed *value* and threads it itself.

```
%s0 = mo.constant <#M.dense_array<42> : tensor<ui64>> : !mo.tensor<[], ui64>      // set_seed(42)
%s  = rmo.reshape(%s0) [newShape = #mosh<ape[1]> : !mosh.ape]                      // -> [1] ui64
%n  = rmo.add(%s, %one_ui64)                                                       // next seed = seed + 1
%sh = rmo.shape_to_tensor() [shape = #mosh<ape[2, 3]> : !mosh.ape] : () -> !mo.tensor<[2], si64>
%m  = mo.constant <#M.dense_array<0.000000e+00> : tensor<f32>>                     // mean
%sd = mo.constant <#M.dense_array<1.000000e+00> : tensor<f32>>                     // std
%r  = rmo.mo.random.normal(%sh, %m, %sd, %s) : (!mo.tensor<[2], si64>, !mo.tensor<[], f32>, !mo.tensor<[], f32>, !mo.tensor<[1], ui64>) -> !mo.tensor<[2, 3], f32>
```

| Python | op | operands (in order) |
|---|---|---|
| `random.gaussian(like, mean, std)` = `random.normal` | `rmo.mo.random.normal` | shape si64[rank], mean f32[], std f32[] (the builder calls this operand `variance`, but Python passes std), seed ui64[1] |
| `random.uniform(like, range=(lo, hi))` | `rmo.mo.random.uniform` | shape si64[rank], lower `like.dtype`[], upper `like.dtype`[], seed ui64[1] |
| `random.set_seed(k)` | no op of its own: `mo.constant` ui64 + `rmo.reshape` to `[1]` | required; without it Python raises *"No seed set!"* |
| `random.SeedType(CPU)` | graph input type `!mo.tensor<[1], ui64>` | per-execution seed: `set_seed(graph_input)` |

- **Rotation:** each random op uses the current seed, then Python emits `rmo.add(seed, 1 : ui64)`
  for the next one, so consecutive ops use seed, seed+1, seed+2 (the last add is dead code).
- Random ops carry no chain, so they are pure functions of (shape, params, seed).
- Integer `like`: draw `normal` in f32, then `rmo.mo.round` + `mo.cast`.
- Module public names: `gaussian`, `normal`, `uniform`, `set_seed`, `SeedType`. Nothing else
  (no bernoulli, randint or dropout).

## 9. Control flow  (`work/inventory/g9_control.txt`, `g13_extra.txt`)

**Chains.** Every graph begins with `%0 = mo.chain.create()` (`!mo.chain`). Control-flow ops carry
the current chain as an *extra last value*: an extra result of `mo.if`, an extra loop-carried
value of `mo.while`. A graph's own `mo.output` does **not** return the chain.

**`ops.cond(pred, out_types, then_fn, else_fn)` → `mo.if`.** `pred` is a `!mo.tensor<[], bool>`
on CPU. Two regions with **no block arguments**: they capture outer values (`%arg1`, `%0`)
directly. Each ends in `mo.yield <results..., chain>`.

```
%1:2 = mo.if(%p : !mo.tensor<[], bool>) -> !mo.tensor<[2, 3], f32>, !mo.chain {
  %c = mo.constant <#M.dense_array<1.000000e+00> : tensor<f32>> : !mo.tensor<[], f32>
  %t = rmo.add(%x, %c) : (...) -> !mo.tensor<[2, 3], f32>
  mo.yield %t, %0 : !mo.tensor<[2, 3], f32>, !mo.chain
} else {
  ...
  mo.yield %e, %0 : !mo.tensor<[2, 3], f32>, !mo.chain
}
mo.output %1#0 : !mo.tensor<[2, 3], f32>
```
generic: `%1:2 = "mo.if"(%p) <{outputParamDecls = #kgen<param.decls[]>}> ({ ...then... }, { ...else... }) : (!mo.tensor<[], bool>) -> (!mo.tensor<[2, 3], f32>, !mo.chain)`;
`"mo.yield"(%t, %0) <{parameters = #kgen<exprs[]>}>`.
`out_types=None` → `%1 = mo.if(...) -> !mo.chain { mo.yield %0 }`. With a side effect in a branch
(buffer store) the branch yields the *new* chain and the other yields the old one.

**`ops.while_loop(init, pred, body)` → `mo.while`.** Carried values are `init ++ [chain]`. Two
regions, condition first; both take the carried values as **block arguments**. The condition
region ends in `mo.while.condition(%bool) <carried...>`; the body ends in `mo.yield <carried...>`.
The body may also capture outer values directly (`rmo.add(%arg4, %arg2)` with `%arg2` from the
enclosing graph).

```
%1:3 = mo.while (%n as %i: !mo.tensor<[], si64>, %x as %v: !mo.tensor<[2, 3], f32>, %0 as %ch: !mo.chain) {
  %c5 = mo.constant <#M.dense_array<5> : tensor<si64>> : !mo.tensor<[], si64>
  %ge = rmo.greater_equal(%i, %c5) ...
  %lt = rmo.mo.not(%ge) ...                                   // i < 5
  mo.while.condition(%lt) %i, %v, %ch : !mo.tensor<[], si64>, !mo.tensor<[2, 3], f32>, !mo.chain
} do {
  ...
  mo.yield %i1, %v2, %ch : !mo.tensor<[], si64>, !mo.tensor<[2, 3], f32>, !mo.chain
}
mo.output %1#0, %1#1 : ...
```
generic: `%1:3 = "mo.while"(%n, %x, %0) ({ ^bb0(%i, %v, %ch): ... "mo.while.condition"(%lt, %i, %v, %ch) : (bool, si64, f32, chain) -> () }, { ^bb0(...): ... "mo.yield"(...) <{parameters = #kgen<exprs[]>}> }) : (...) -> (...)`.
No `outputParamDecls` on `mo.while`; `mo.while.condition` has no properties.

## 10. Subgraphs  (`work/inventory/g10_subgraph.txt`)

A subgraph is a **second top-level `mo.graph` in the same `builtin.module`**, printed after the
parent, marked with the unit property **`isSubgraph`**, `sym_name` = the name given to
`add_subgraph`. Python appends a `!mo.chain` input and a `!mo.chain` output to its signature;
the body returns its input chain unchanged (it has its own unused `mo.chain.create`).
`argument_names` lists only the user inputs, while `result_names` also names the chain output.

```
module attributes {mo.device_info_mapping = {...}} {
  mo.graph @main(%arg0: !mo.tensor<[2, 3], f32>) -> !mo.tensor<[2, 3], f32> attributes {...} {
    %0 = mo.chain.create()
    %1:2 = mo.call @add_one(%arg0, %0) : (!mo.tensor<[2, 3], f32>, !mo.chain) -> (!mo.tensor<[2, 3], f32>, !mo.chain)
    %2:2 = mo.call @add_one(%1#0, %1#1) : (!mo.tensor<[2, 3], f32>, !mo.chain) -> (!mo.tensor<[2, 3], f32>, !mo.chain)
    mo.output %2#0 : !mo.tensor<[2, 3], f32>
  }
  mo.graph @add_one(%arg0: !mo.tensor<[2, 3], f32>, %arg1: !mo.chain) -> (!mo.tensor<[2, 3], f32>, !mo.chain) isSubgraph attributes {_kernel_library_paths = [], argument_names = ["input0"], result_names = ["output0", "output1"]} {
    %0 = mo.chain.create()
    ...
    mo.output %3, %arg1 : !mo.tensor<[2, 3], f32>, !mo.chain
  }
}
```
- Call, custom: `mo.call @callee(args..., chain) [prefix = "layer0."] : (...) -> (results..., !mo.chain)`
  (`[prefix = ...]` printed only when non-empty).
- Call, generic: `"mo.call"(%a, %0) <{callee = @add_one, outputParamDecls = #kgen<param.decls[]>, prefix = ""}>`.
- Subgraph generic: `"mo.graph"() <{counter = 0 : i64, functionType = (..., !mo.chain) -> (..., !mo.chain), inputParameters = #kgen<param.decls[]>, isSubgraph, resultParameters = #kgen<param.decls[]>, signature = !kgen.generator<(..., !mo.chain) -> (..., !mo.chain)>, sym_name = "add_one"}>`.
- The chain is threaded call to call (`%1#1` feeds the second call), so calls are sequenced.
- `prefix` is a string property: the weight-name prefix used by `max.nn` modules.

## 11. Symbolic dimensions  (`work/inventory/g11_symbolic.txt`)

- Graph header, custom: `mo.graph @g<batch, k, n>(%arg0: !mo.tensor<[batch, k], f32>, ...)`.
  The `<...>` list holds every symbolic name used by the inputs, in first-use order.
- Generic: `inputParameters = #kgen<param.decls[batch : !kgen.scalar<si64>, k : !kgen.scalar<si64>, n : !kgen.scalar<si64>]>`,
  `resultParameters = #kgen<param.decls[]>`, `functionType` uses the names, and Python's
  `signature = !kgen.generator<(!mo.tensor<[batch, k], f32>, ...) -> ...>` also uses the names.
  (MAX's text parser instead derives the positional form `!kgen.generator<<scalar<si64>, ...>(!mo.tensor<[*(0,0), *(0,1)], f32>, ...)>`,
  as in `capi/models/sym_mlp.generic.mlir`; both are what MAX itself produces.)
- Ops need nothing extra: `rmo.matmul(%a, %b) : (!mo.tensor<[batch, k], f32>, !mo.tensor<[k, n], f32>) -> !mo.tensor<[batch, n], f32>`.
  Dims must match *by name*: `[batch,k] @ [j,n]` is a build error; use
  `rmo.rebind_tensor_shape(%a) [message = ""] -> [batch, j]` first.
- Derived dims are expressions in types and attributes: `mul_no_wrap(batch, 3)` (reshape),
  `add(a, b)` (concat), `add(n, -2)` (slice).
- **New dims introduced by an op** (data-dependent): the op declares them. Custom
  `rmo.mo.range<() -> m>(...)`, `rmo.rebind_tensor_shape<() -> m>(...)`, `rmo.mo.arg_nonzero<() -> nz>(...)`;
  generic `outputParamDecls = #kgen<param.decls[m : !kgen.scalar<si64>]>`. The graph then gets
  `counter = 16 : i64` and the dim may appear in a graph output type (`!mo.tensor<[m], si64>`)
  with `resultParameters` still empty.
- Reductions over a symbolic axis give 1 there: `[batch, 3]` axis 0 → `[1, 3]`.
  Broadcasting also works symbolically: `[batch, 1] + [1, n]` → `[batch, n]`.

## 12. Custom kernels  (`work/inventory/g12_custom.txt`)

`ops.custom(name, device, values, out_types, parameters)` → `mo.custom`:

```
%1:2 = mo.custom [symbol = "my_kernel", parameters = {dt = f32, eps = #M.dense_array<5.000000e-01> : tensor<f32>, flag = true, mode = "fast", n = 3 : index}](%x) : (!mo.tensor<[2, 3], f32>) -> (!mo.tensor<[2, 3], f32>, !mo.tensor<[2], si64>)
```
generic: `"mo.custom"(%x) <{device = #M.device_ref<"cpu", 0>, outputParamDecls = #kgen<param.decls[]>, parameters = {...}, symbol = "my_kernel"}>`.
- Parameter encodings: bool → `true`, int → `3 : index`, float → rank-0 f32 dense array, str →
  string, DType → a type (`f32`).
- `device` is only visible in the generic form.
- Python checks `symbol` against the loaded kernel libraries while building: an unknown name
  raises *"no kernel registered for 'my_kernel'"*. To print these entries I stubbed that check.
  Built-in kernels reached the same way, without the stub: `mo.acos`, `mx.argsort`, `repeat_interleave`.
- `inplace_custom` (side effects on a buffer) adds the chain: `%c2 = mo.custom [symbol = "my_inplace"](%buf, %x, %c) : (!mo.buffer<[2, 3], f32>, !mo.tensor<[2, 3], f32>, !mo.chain) -> !mo.chain`,
  with buffers from `mo.buffer.create : !mo.buffer<[2, 3], f32>` and read back by
  `%t, %c3 = rmo.mo.mutable.load(%buf, %c2)`. Stores are `rmo.mo.mutable.store(%buf, %t, %c) -> !mo.chain`.

- `ops.print(x, "x")` → `%c1 = mo.debug.tensor.print(%0, %x) [label = "x"]`. The chain comes
  first and the op returns a new chain.
- `ops.transfer_to(x, CPU)` on a CPU value emits nothing.

## Compositions (Python API, not one op)

`div` on ints (cast both to f64), `floor_div` (float: div + floor; int: 13 ops), `a < b` and
`a <= b` (not of `>=` / `>`), `outer`, `stack`, `chunk`, `squeeze`/`unsqueeze`/`flatten` (all
`rmo.reshape`), integer indexing `x[i]` (slice + reshape), `pad` (the paddings vector is built from
constants + concat), `tile` (shape_to_tensor + tile), `hann_window`, `conv2d` (rebind + conv, and
a bias add), `conv2d_transpose` (rebind + conv_transpose, and broken bias), random ops (seed
reshape + shape_to_tensor + constants + rotation add), integer `gaussian` (normal + round + cast),
`repeat_interleave` with axis=None (reshape first). Ops the API routes through `mo.custom` instead
of a dialect op: `acos` (`mo.acos`), `argsort` (`mx.argsort`), `repeat_interleave`.

## 14. Round 2: scatter along an axis, top-k, and graphs on a GPU  (`work/inventory/g15_round2.txt`, `g16_gpu.txt`)

Scripts: `capi/scripts/inventory/round2_ops.py`, `gpu_ir.py` (MAX's Python API builds GPU graphs
without a GPU).

| Python | IR | notes |
|---|---|---|
| `scatter(x, upd, idx, axis)` | `rmo.mo.scatter(%x, %upd, %idx) [axis = 1]` | element-wise along the axis: indices shaped like the updates; generic `axis = 1 : index` |
| `scatter_add(x, upd, idx, axis)` | `rmo.mo.scatter.add(%x, %upd, %idx, %axis)` | the axis is a rank-0 si64 **operand** |
| `top_k(x, k, axis)` | `rmo.top_k(%x) [k, axis]`, two results | si64 attributes; sorted values with k = an axis's size, any axis on the CPU |
| `bottom_k(x, k)` | `rmo.mo.bottom_k(%x, %k, %axis, %sorted)` | k, axis, sorted as rank-0 operands |

**On a GPU** (`DeviceRef.GPU()`):
- Every data tensor's type names the device: `!mo.tensor<[2, 3], f32, gpu:0>`, graph arguments and
  results included. In bytecode the type is its text, so nothing else changes.
- Element-wise scalar constants are on the GPU too (`mo.constant ... : !mo.tensor<[], f32, gpu:0>`).
- Operands that are parameters stay on the host, typed without a device: transpose permutations,
  pad amounts **and pad value**, `band_part`'s bounds, `bottom_k`'s k/axis/sorted, `scatter.add`'s
  axis, `range`'s bounds (its result is on the GPU), `random`'s shape and bounds, `layer_norm`'s
  epsilon, `rmo.shape_to_tensor`.
- `mo.custom` names the device: `device = #M.device_ref<"gpu", 0>`.
- The conv filter's rebound type keeps its layout after the device:
  `!mo.tensor<[3, 3, 2, 4], f32, gpu:0, {layout = #mo.layout<RSCF>}>`.
- `rmo.mo.transfer[%chain] %x : ... to <"cpu", 0>` moves a value, returning it and a new chain. A
  random seed computed from host constants is transferred to the GPU this way.
- **Predicates must be on the CPU**: `ops.cond` and `ops.while_loop` refuse a GPU predicate ("must
  reside on CPU"); MAX's own graphs transfer it first.
- `top_k` on a middle axis still builds for a GPU; the kernel's docstring says only the last axis is
  supported there.
- The module carries `mo.device_info_mapping = {cpu = #M.device_info<...>}` even when built for a GPU
  without one; eco-lab/tensor writes no such attribute (what a real GPU needs is checked in M4).

eco-lab/tensor (`Tensor.Internal.Device`, `Graph.toBytecodeOn`) writes exactly this placement; `make
check-gpu-ir` compares every op of every op-check family written for GPU 0 with MAX's placement for
the same op (1,849 ops, 0 differ) and reads each graph back through `mlir-opt`. Branches and loops,
and top-k off the last axis, are refused on a GPU until M4.
