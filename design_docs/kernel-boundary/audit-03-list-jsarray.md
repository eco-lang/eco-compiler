## Key findings

1. **`Elm_Kernel_List_cons` is the single biggest miss in the surface: 4921 call sites in the self-compiled compiler, and MLIR already has the inline path it needs.** `::` is an *operator imported from `List`* (`Compiler/Elm/Compiler/Imports.elm:34`), so every `x :: xs` in Elm source becomes `List.cons` → `Elm.Kernel.List.cons`, LSS-devirtualized to a direct `Elm_Kernel_List_cons*` call (whitelist at `MonoSolver/Translate.elm:1862`). `eco.construct.list` is emitted **only for list literals** `[a,b,c]` (`Generate/MLIR/Expr.elm:1017,1031`).

2. **HEAP_034 inline nursery allocation does *not* currently cover cons.** `ListConstructOpLowering` (`EcoToLLVMHeap.cpp:445-456`) emits marker + composed header + two fresh field stores — zero runtime calls. The C++ path instead pays: HPtr encode/decode, a `eco_g_cons_sites` tally branch, an 8-byte `memcpy` into `roots[2]`, a statepointed `eco_alloc_with_roots` call, header writes, a `memcpy` readback, and `Allocator::wrap` (`HeapHelpers.hpp:630-646`). No LTO closes this: the C++ kernel is a separately-linked static library (the driver's internalize+DCE at `EcoNativeDriver.cpp:232-240` runs on the Elm module only).

3. **Fix for #1 is a one-liner-shaped change**: `kernelIntrinsic` (`Generate/MLIR/Intrinsics.elm:312-332`) has no `"List"` arm at all — the intrinsics doc states this explicitly (`design_docs/theory/intrinsics_theory.md:260`). Adding `("List","cons",[head,tail])` → an `EcoConstructList`-emitting intrinsic reuses the existing head-kind derivation (`Generate/MLIR/KernelAbi.elm:310-317`) and the existing ABI shape guard (`Translate.elm:1883` already proves tail and result are boxed `!eco.value`).

4. **Trap for #3**: `EcoListTemplate` skips `eco.construct.list` ops that carry live-root hints (`EcoListTemplate.cpp:147-152` → `wcConsRoots` bail) but happily matches the kernel-call form (`kernelConsKind`, `:98-113`). If cons switches to `construct.list` *with* `emitSafepointHints`, the cons-accumulator → scratch-chunk rewrite (582 `eco_scratch_push_boxed` + 491 `eco_scratch_mark` sites today) silently stops firing. Either emit without root hints or relax the pass first.

5. **`eco.array.get` / `set` / `length` are confirmed real and the C++ twins are dead on direct paths.** `ArrayLengthOpLowering` / `ArrayGetOpLowering` are fully inline (resolve + GEP + load; `EcoToLLVMHeap.cpp:1219-1302`); `ArraySetOpLowering` is a clone call plus inline GEP/store (`:1308-1399`). Zero relocations in the self-compile for `Elm_Kernel_JsArray_{length,unsafeGet,unsafeGet_Int,unsafeSet,unsafeSet_*,push,push_*,slice,slice_Int,appendN,appendN_Int,singleton_*}` — **18 dead JsArray symbols**. The intrinsic is also strictly cheaper: `unsafeGet` in C++ *allocates a box* for primitive-kind arrays (`JsArrayExports.cpp:219`), the intrinsic does not.

6. **The `Elm::Kernel::List::` namespace in `List.cpp` is ~80% dead code.** `map2/map3/map4/map5/sortBy/sortWith/fromArray/toArray` (lines 22-309) have **no callers anywhere in the repo** — the exports use `kernelListMapN` and the ListExports sort drivers instead. Only `List::cons` survives. `ListOps::sortBy`/`sortWith` are reachable *only* through that dead code. `ListOps::{head,tail,getAt,last,map,indexedMap,filterMap,intersperse,partition,unzip,member,maximum,minimum,map2,map3,foldl,all,any,repeat,singleton,toVector,product}` have zero non-test callers.

7. **Kind-collapse family (latent correctness).** `alloc::listFromUnboxables`/`listFromPointers` take a `bool is_boxed`, which the `cons(bool)` overload maps to head_kind ∈ {0,1} only (`HeapHelpers.hpp:650`). So `ListOps::take` (**always** — it has no chunk path, `ListOps.cpp:373-386`) and `append`/`concat` on their non-chunk fallbacks tag Float/Char heads as **Int**. Raw bits survive and `eco_cons_head_f64` ignores the tag (`RuntimeExports.cpp:4151`), so compiled Elm reads are fine — but any kind-dispatched *re-boxing* is not: `listToVectorU64` → `boxElement(head, 1)` produces a `Tag_Int` from a double, which then reaches `Utils::compare`'s tag dispatch, `Debug.toString`, and `pushUnboxedResult`. Concrete path: `List.sortBy f (List.take n floatList)`. Same defect in `Elm_Kernel_List_fromArray:349` and — worse, unconditionally — `Elm_Kernel_JsArray_unsafeSet:256` / `_push:304` which force `header.unboxed = 1` for *any* unboxed source array (kind 2/3 → 1). The `elm_array_*` trampolines and `copyForUnsafeSet` do it correctly; only the legacy (now dead-on-direct-path) exports are wrong.

8. **`Elm_Kernel_List_sortBy` can violate strict weak ordering.** `ListExports.cpp:730-736` passes `nullptr` for embedded-constant keys, and `Utils::cmp` returns `-1` when `!a` *before* testing `b` (`Utils.cpp:305-306`). With two constant keys — e.g. `List.sortBy identity ["", "", "x"]` (`Const_EmptyString`) or sorting records whose key is `[]` (`Const_Nil`) — `comp(a,b)` and `comp(b,a)` are both true, which is UB for `std::stable_sort` (libstdc++'s `__unguarded_linear_insert` can run off the front of the buffer). Fix: compare the constant bit patterns first, or make `cmp` return `0` when both are null.

9. **`reverse/append/concat/take/drop` are already Elm source** — the C++ is an opt-in *replacement*, not the only implementation. `Functions.elm:318-338` rewrites recognized elm/core specializations into saturated kernel calls under `config.list.chunks`, which has been **default `True` since Aug 3** (`Compiler/Eco/Config.elm:324`). Recognition is by specialization origin via the registry, so user functions named `reverse` are never touched; `drop` is never shunted because elm/core `drop` compiles to `MonoTailFunc`.

10. **What reverting the shunt would cost — and why it may cost less than it looks.** The shunt buys dense chunk production (`listChunkChain` + `ListChainWriter`: one `ListBacking` + one `ConsChunk` view per ≤LOT run instead of n cells), the O(1) `length` from a view's total-length field, and O(spine-node) `drop`. But `EcoListTemplate` **already produces exactly the same dense chunks from compiled Elm loops** (`eco_scratch_mark`/`push`/`finish`), and `reverse = foldl cons []` (`elm/core List.elm`) is precisely the cons-accumulator shape that pass targets. So Elm-source `reverse` would very likely keep the chunk win *and* regain inliner/GlobalOpt/LSS/borrow visibility. `append`/`concat`/`take` are the weaker cases: `concat = foldr append []` and `take = takeFast` are non-tail recursive with nested `cons x (cons y …)`, which `EcoListTemplate` does not match — those genuinely lose chunking.

11. **A cheaper intermediate exists for `take`/`append`/`concat`:** they walk the source twice (probe + fill) in C++, while the compiled-Elm + scratch route walks once. The shunt is not obviously a win on wall for these; it was justified by object count. Measuring `reverse` alone (468 sites, the census's biggest cons producer) against Elm-source + `EcoListTemplate` is the highest-value experiment here.

12. **`map2..map5`: an Elm-source implementation would be both safer and more optimizable.** The current driver (`ListExports.cpp:432-590`) is 160 lines of hand-rolled GC discipline: rolling-prefix root ranges, a deliberate *refusal* to use the `cb[]` snapshot for boxed heads (`:481-487`), a re-read of every boxed head after Phase-1 boxing (`:520-526`), and a post-callback `listStepAt` from the rooted `(node, idx)` cursor rather than the pre-call `tail` (`:571-578`). Every one of those is a manual re-derivation of what statepoint-based rooting gives for free in compiled Elm. Elm source (`map2 f xs ys = case (xs,ys) of (x::xr, y::yr) -> f x y :: map2 f xr yr; _ -> []`) is safe by construction, becomes a cons-accumulator loop that `EcoListTemplate` can chunk, and exposes `f` to LSS devirtualization instead of routing it through `eco_apply_closure_eval`.

13. **`sortBy`/`sortWith` current idiom:** materialize into a contiguous `vector<HPointer>`, `pushStackRootRange` the whole buffer, sort a `vector<size_t>` of **indices** (never the HPointers), and re-read the rooted buffer on every comparison — because `std::stable_sort` moves elements through an internal temporary that the root scanner cannot see. `sortBy` additionally re-pins after every key-extraction closure call; `sortWith` roots by-value copies `aRoot`/`bRoot` inside the comparator. Elm-source is the right target (a merge sort in Elm, as elm/core would have without the JS kernel): all rooting becomes statepoint-derived, the comparator is inlinable, and the index indirection disappears. Not implementable as an MLIR intrinsic — hence Elm-source rather than Feasible.

14. **`fromArray`/`toArray` are effectively identity.** Both take the pass-through branch on every real call site (`ListExports.cpp:327`, `:370`) — they exist because the Elm source wraps JS-kernel calls that returned JS Arrays. Folding them to identity at MLIR generation when the argument's MonoType is `List a` removes 2 symbols and 2 cross-ABI calls for free.

15. **HOF safety note that generalizes:** every HOF in this surface correctly (a) roots the closure *before* the first allocation, (b) re-resolves the container after every callback, and (c) uses `alloc::allocArrayBuilder` + `BuilderGuard` to pin half-built arrays to the nursery (HEAP_BUILDER_001/003). The one structural weak point left is that these are *conventions*, checked only by `ECO_HEAP_VALIDATE`; moving the drivers to Elm source replaces the convention with compiler-enforced statepoint liveness.
