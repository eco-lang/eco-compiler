# Compute benchmarks

Pure-computation benchmarks (no IO) for comparing eco with the official Elm compiler. Each
workload in `src/` is a module exposing `bench : Int -> Bool` that uses only `elm/core`,
`elm/json`, `elm/bytes` and `elm/parser`, so the same source builds with both compilers. `bench`
does the work at the given size and checks its own result.

The default sizes make every workload take at least 200 ms on the official compiler's
JavaScript, each run in a process of its own.

## How results are checked

Each workload checks itself as strongly as it can, at whatever size it runs:

- Exactly at every size, by a closed form or an independent recomputation: fib, binary-trees,
  list-map, list-filter, list-fold, dict, sort, float-sum (within its rounding error),
  merkletrees, brainfuck (the program's known output), bytes-static and bytes-dynamic (the
  generated bytes), json (the generator's averages, exactly), expr-parser and sexpr (the
  generator's value), dijkstra (the shortest-path certificate), word-freq (counts recomputed from
  the generator), sudoku (a direct validity check of every solution), flood-fill (union-find over
  the same grid), matmul (a closed form, within rounding), floyd-warshall (symmetry, zero diagonal
  and four rows against BFS), unicode-string (lengths, sums and positions from the code points;
  only the ASCII part of `toUpper`), base64 (the round trip and the RFC vectors), utf8-bytes,
  json-shapes and json-decoders (the round trip to the generated value), json-parser (agreement
  with `Json.Decode`), dict-algebra, set-algebra and popcount (closed forms), dict-int,
  dict-string, dict-tuple and set-distinct (recomputed without the structure), shuffle-sort (a
  permutation, and its last 100 positions against a sparse replay of the first 100 swaps),
  array-build (closed-form rotations), csv-split and csv-parser (the generator's sums),
  string-append, string-join and string-concat (length and checksum combined from the pieces),
  binary-format (the round trip and every chunk's CRC), json-dict (the generator's sums),
  json-encode (both texts' lengths from the value, and the round trip) and lexer (the
  generator's token counts). spectral-norm must lie within `6 / n^3` of its limit (a bound
  measured with a C program from 1 to 5,500).
- Exactly against a table that covers every feasible size: fannkuch-redux (1-12 items, from the
  standard C algorithm), nsieve (2-14, from a separate sieve), n-queens (up to 18, OEIS
  A000170), life (every generation to 1,103, after which the R-pentomino has 116 cells for
  good) and nsieve-bits (nsieve's table). Larger fannkuch-redux, nsieve, nsieve-bits and n-queens
  sizes fail the check.
- Exactly at the sizes in a table, and by an invariant elsewhere: mandelbrot (counts from a C
  program; elsewhere a plausible share of the grid), nbody (published outputs; elsewhere the
  published initial energy and energy conservation), lru (elsewhere hits + misses = rounds),
  fasta (elsewhere the output's length), k-nucleotide and revcomp (the Benchmarks Game's
  published outputs and a Python reference; elsewhere every k's counts add up to the positions,
  and reverse-complementing twice gives the input back), sha256 (Python's `hashlib`; elsewhere
  the FIPS test vectors), crc32 (Python's `zlib`; elsewhere the standard check value),
  levenshtein (a Python implementation; elsewhere the structured pairs exactly and every edited
  pair within its bounds), prng (a Python implementation; elsewhere Marsaglia's published first
  outputs) and adler32 (Python's `zlib`; elsewhere the standard example). At sizes outside their
  tables these can pass a subtly wrong result.

Each module's documentation says where its table comes from. The check runs inside the timed
region, and costs little next to the work, except revcomp's, which reverse-complements
everything a second time.

## Run the comparison

Needs `eco`, `elm` (0.19.1) and `node` on the PATH:

    node run.mjs                         # build, then run every workload on every backend
    node run.mjs fib nbody --runs 25     # some workloads, more samples
    node run.mjs --skip-elm              # without the official compiler

The table shows, per workload, the median time in milliseconds on the official compiler's
JavaScript (`elm`), eco's JavaScript (`eco-js`) and eco's native code (`eco-native`), and how many
times faster eco native is than `elm`. If a workload's check fails on any backend, `run.mjs`
exits with status 1. All figures also go to `build/results.json`. Set `ECO` or `ELM` to use
binaries that are not on the PATH.

`run.mjs` runs each workload on each backend in a process of its own, so a workload's timings do
not depend on the workloads before it (a heap left full, GC debt, JIT state) or on their order.
Inside that process, the warm-up runs and then the timed runs share the heap and the JIT, which
is what the warm-up is for. `./bench` on its own runs all its workloads in one process.

eco times itself with `Time.now`, which has 1 ms resolution; the official build is timed by
`run.mjs` with `process.hrtime`.

## eco only

    eco make src/Bench.elm --output=bench
    ./bench                              # all workloads, as a table
    ./bench --list                       # the workloads and what each one stresses
    ./bench --print nbody=1000           # a standard benchmark's usual text output
    ./bench --json fib=30                # results as JSON (`--list --json` lists the workloads)

## Layout

- `src/`: the workloads, and `Bench.elm`, the eco/system program that times them.
- `elm/`: the project for the official compiler; `ElmBench.elm` runs any workload through ports.
- `run.mjs`: builds all three, runs each workload on each in a fresh process, and prints the
  table.

The first nine workloads come from the alm compute benchmarks; nbody, spectral-norm,
fannkuch-redux, nsieve, merkletrees, lru and fasta from the Programming Language Benchmarks suite
(each builds that suite's exact text output, which `--print` shows); n-queens counts the
solutions of the n-queens puzzle. The rest are the first batch of
`plans/benchmark-suite-expansion.md`, one per area: k-nucleotide and revcomp (Benchmarks Game;
Dict and String), life (Set), brainfuck (kostya/benchmarks; Array), sha256 (FIPS 180-4;
Bitwise), bytes-static and bytes-dynamic (elm/bytes, with and without eco's decoder fusion), json
(kostya/benchmarks; elm/json) and expr-parser (elm/parser). Batch 2 adds two more per area:
dijkstra and word-freq (Dict), sudoku (plb2, Norvig) and flood-fill (Set), matmul (plb2,
kostya) and floyd-warshall (Array), levenshtein and unicode-string (String), nsieve-bits
(Shootout) and crc32 (Bitwise), base64 (kostya) and utf8-bytes (Bytes), json-shapes
(nativejson-benchmark's corpus shapes) and json-decoders (JSON), json-parser and sexpr (Parser).
Batch 3 completes the plan: dict-algebra and dict-int / dict-string / dict-tuple (Dict),
set-algebra and set-distinct (Set), shuffle-sort and array-build (Array), csv-split and
string-append / string-join / string-concat (String), prng and popcount (Bitwise),
binary-format and adler32 (Bytes), json-dict and json-encode (JSON), csv-parser and lexer
(Parser).
